Multi-terminal test runbook

Run the real multi-user model: each operator in their own terminal, on their own clone, pushing to the same branch concurrently — not sequenced by one coordinator. This is the honest test the single-session simulation could not be.

This is a test harness, not part of AI-gile. It lives with the ledger-wallet toy. Nothing here is a canonical methodology change — it's a script for humans (or separate Claude Code sessions) to drive the operators independently.

00What this tests that the simulation didn't

The earlier runs drove every operator from one session, so collisions were staged and pushes were sequenced. Open these terminals for real and you get genuine concurrency.

Real push races

Two operators push the same branch within seconds — the loser gets a true non-fast-forward rejection, not one I arranged.

Interleaved ledgers

Concurrent signed claim/phase events land in .aigile/manifests/ without a coordinator serializing them — the AGV-328/329 stress.

The new command in anger

Each terminal provisions itself with one ag-operator join — the fix, used the way it's meant to be.

Independent judgement

Operators make their own calls; nobody sees the others' context. That's what multi-user is for.

01Prerequisites (once, already done)

  • Toy repo on GitHub: git@github.com:Stephen-Kamau/ledger-wallet.git, branch dev.
  • multi_user_enabled is ON and the signed flag is committed (travels to clones).
  • Five operators enrolled in the signed roster: amara, dakari, kofi, nia, zola.

02Each operator's terminal

Every operator runs the same three moves: clone, join in one command, then work their stream. Change only the login.

Amara — core + adapterarchitect · core/**

$ git clone git@github.com:Stephen-Kamau/ledger-wallet.git amara && cd amara
$ ag-operator join --login amara --key ~/keys/amara.json \
      --email amara@ledger.test --name "Amara Okeyo"
ag-operator join: amara is ready (git Amara Okeyo <amara@ledger.test>, keystore identity present, multi_user on)

03The concurrency drill (the real test)

Have two operators edit the SAME file at the same time, then both push. This is what the simulation staged — now it happens for real.

Amara & Dakari — both touch core/ledger.gocollision
# both add a method to the Ledger interface, commit, then race to push:
[amara] $ git push origin dev          # wins: fast-forward
[dakari] $ git push origin dev         # ! [rejected] (non-fast-forward)
[dakari] $ git pull --rebase origin dev  # CONFLICT in core/ledger.go
[dakari] $ $EDITOR core/ledger.go       # resolve: keep BOTH methods
[dakari] $ go test ./... && git rebase --continue && git push origin dev  # both land

Expected: the overlap gate WARNS at plan time, git blocks the clobber at push, the merge keeps both edits. If anything else happens — a silent overwrite, a broken ledger, a gate that fired wrongly — that's a real issue to capture.

04Where the logs are

Signed event ledger (automatic)

.aigile/manifests/<base>.events.jsonl — every claim / phase event, with actor{login,email}, wall timestamp and sig. The machine truth; one per operator's burst base. These merge when operators push.

Activity log (curated)

docs/operators-activity-log.md — a human-readable, timestamped per-operator table. In the real model each operator appends their own rows; it is not auto-captured.

Each separate terminal also has its own shell history and (if a Claude Code session) its own transcript — the per-operator command record the single-session run could not produce.
